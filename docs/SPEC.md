# SMS-Man Auto 배포 준비 스펙 시트

- 문서 버전: 1.0
- 작성일: 2026-09-07
- 상태: 1단계 기획 산출물. 구현·4개 병렬 QA·배포는 아직 수행하지 않음.
- 저장소: https://github.com/JaeM-beginner/sms-man-auto
- 점검 기준 커밋: `1131a44887c5cb50a01b6abd427dcc348fe6d425`
- 대상: Python 3.12+ / Tcl·Tk 기반 Windows 데스크톱 앱
- 목적: 비용 발생과 활성 번호를 사용자가 통제하고, 민감정보를 보호하며, 타인에게 배포할 수 있는 상태로 만든다.
- 규칙: MUST는 출시 필수, SHOULD는 권장, LATER는 후속 범위이다. 이 문서의 기본값은 기획 제안이며 기존 구현 사실과 구분한다.

## 1. 작업 단계와 범위

| 단계 | 산출물 | 완료 조건 |
|---|---|---|
| 1. 스펙 | 본 문서 | 요구사항·기본값·수용 기준·검증 절차·미결정 항목이 명시됨 |
| 2. 구현 | 코드, 회귀 테스트, 안내 문서, CI, 배포 후보 | 요구사항별 구현 및 증거 연결 완료 |
| 3. 독립 QA | 무맥락 서브 에이전트 4개 보고서 | 같은 후보 커밋을 병렬 검토하고 결함 수정 후 필요한 재검증 완료 |
| 4. 최종 보고 | 요구사항 추적표, 결함 처리표, 출시 판정 | 미검증·보류·잔여 위험까지 구분해 보고 |

이번 요청은 1단계만 수행한다. 이 문서는 후속 구현자가 대화 기록 없이 사용할 수 있어야 한다. 스펙 작성 완료는 제품 배포 준비 완료를 뜻하지 않는다.

### 포함

- 발급·폴링·중지·거절·창 종료의 상태 관리와 비용 제한
- API 계약과 오류 처리, 토큰·번호·인증코드 보호
- 최소한의 개인정보 안내, 문의, 보안 신고, 이용조건, 라이선스 결정 절차
- 재현 가능한 테스트 및 Windows 배포 후보 검증
- 4개 독립 리뷰의 전달 계약과 최종 완료 기준

### 제외

- 웹서비스 전환, 자체 회원가입·서버·결제·데이터베이스
- 타 사이트 가입 자동화, CAPTCHA 우회
- 텔레메트리, 클라우드 로그 수집, 자동 업데이트
- 토큰 저장, 장기 인증번호 이력 저장
- 대규모 UI 재설계, 국가·서비스 검색 UI 및 잔액 조회는 LATER

## 2. 현재 확인된 사실과 한계

| ID | 기준 커밋에서 확인한 내용 | 근거·검증 수준 |
|---|---|---|
| F-01 | 토큰 마스킹, 파일 미저장, 기본 HTTPS, 표준 라이브러리 사용 | `sms_man_app.py`, `README.md` 정적 확인 |
| F-02 | SMS 대기 120초 후 거절·재발급 반복, 총량 제한 없음 | `Poller._run` 정적 확인 |

| F-05 | 외부 오류 메시지에 포함된 가짜 토큰이 그대로 예외 메시지에 남음 | 실제 토큰 없이 모의 응답으로 확인; 실제 유출이 확인된 것은 아님 |
| F-06 | 인증코드 자동 복사, 활동 기록에 전화번호 전체 표시 | UI 이벤트 처리 정적 확인 |
| F-07 | limits의 공식 목록 응답을 공통 JSON 처리기가 거부함 | 공식 예시 입력 재현; 실제 계정 조건별 응답은 미확인 |
| F-08 | 기존 테스트 13개 통과 | unittest 실행; 실패·경합·실제 Windows UI 검증을 대체하지 않음 |
| F-09 | LICENSE·개인정보·지원·보안 문서, CI 파일, GitHub Release 없음 | 기준 파일 목록 및 Releases 조회 |

미확인: 과거 전체 Git 이력의 비밀정보, GitHub 보안 설정, 유료 API 실제 동작·환불, Windows UI/EXE, POST 본문 지원 세부 동작. 구현 시작 시 HEAD 변경 여부를 확인하고 차이를 기록한다.

## 3. 제품 기본 정책

| 항목 | v1 기본값·정책 |
|---|---|
| 자동 재발급 | OFF. 사용자가 실행 전 켠 경우에만 허용 |
| 최대 발급 수 | 기본 1회. 자동 재발급 ON 시 사용자 지정 1~5회. 성공적으로 얻은 활성 번호 수 기준 |
| 재고 없음 재시도 | 3초 간격, 최대 20회. 전체 실행 시간 제한도 적용 |
| SMS 대기 | 활성 번호별 120초 |
| 전체 실행 시간 | 기본 600초. 초과 시 신규 발급 금지, 기존 번호는 정리 절차로 이동 |
| 요청 시간 제한 | 기본 15초. 정리 작업은 별도 제한된 대기 시간과 실패 상태를 가짐 |
| 최대 단가·통화 | 실행 전 사용자 입력 필수. 임의 금액 기본값 없음. 공식 API 지원 형식 확인 후 적용 |
| 가격 안내 | 조회 가격은 참고값, 서버가 강제하는 maxPrice가 구매 상한임을 구분 |
| 구매 확인 | 국가 ID, 서비스 ID, 통화, 단가 상한, 최대 발급 수, 자동 재발급 여부 표시 |
| 인증코드 복사 | 자동 복사 OFF, 수동 버튼 제공. 선택 시 해당 세션에서만 자동 복사 |
| 민감정보 저장 | 토큰·번호·SMS·인증코드 파일 저장 없음. 설정도 이번 버전에서는 세션 한정 |
| 활동 기록 | 전화번호 마스킹, 인증코드·토큰 출력 금지, 최근 500행 제한 |

단가 상한 × 최대 발급 수는 신규 발급의 계산상 상한이다. 환율·수수료·제공자 정책까지 포함한 보장 총액이나 환불 보장으로 표시하지 않는다. 동일 계정을 다른 앱에서 사용하는 비용은 통제할 수 없다. 모든 한도는 한 실행 기준이며 사용자 재시작으로 새 실행이 시작된다.

## 4. 상태와 동시성 계약

| 상태 | 가능한 사용자 동작 | 전이·불변 조건 |
|---|---|---|
| IDLE | 설정·시작·재고 조회 | 확인 후 REQUESTING |
| REQUESTING | 중지 | 발급 성공→WAITING_SMS. 요청 결과 불명→UNRESOLVED. 중지 후 늦은 성공→STOPPING |
| WAITING_SMS | 중지·거절·번호 복사 | 코드 수신→SUCCESS. 시간 초과→REJECTING |
| STOPPING | 상태 확인 | 신규 요청 금지. 진행 요청 반환을 처리하고 미사용 번호 정리 |
| REJECTING | 상태 확인 | 거절 확인 후 종료 또는 허용된 재발급. 실패·불명→UNRESOLVED |
| SUCCESS | 결과 복사·새 실행·정보 지우기 | 성공 결과 유지. 자동 다음 구매 금지 |
| STOPPED / ERROR | 새 실행·정보 지우기 | 미정리 활성 번호가 없을 때만 새 실행 가능 |
| UNRESOLVED | 정리 재시도·SMS-Man 계정에서 확인·종료 | 자동 재발급 금지. 해결 또는 명시적 외부 확인 없이는 시작 차단 |

- MUST: 각 실행에 run_id를 부여하고, 활성화 관련 이벤트는 activation_id도 포함한다. 이전 실행의 늦은 이벤트가 새 실행의 UI를 변경하지 않는다.
- MUST: 번호 구매·SMS 조회·거절은 하나의 실행 제어 흐름에서 순서를 보장한다. UI 스레드는 HTTP를 직접 호출하지 않는다.
- MUST: 시작 연타로 중복 worker/구매가 생기지 않는다. 거절 연타도 중복 전송을 만들지 않는다.
- MUST: 중지 이후 이미 진행 중인 요청은 취소되었다고 단정하지 않는다. 늦게 받은 활성 번호도 관리한다.
- MUST: 거절 성공 후 그 번호를 다시 폴링하거나 다시 거절하지 않는다.
- MUST: 코드 수신과 거절이 경합하면 확정 상태를 기준으로 처리한다. 거절 완료 후 도착한 코드 이벤트는 성공으로 노출하지 않는다. 코드 수신 완료 뒤 자동 거절로 환불을 약속하지 않는다.
- MUST: SUCCESS 상태의 provider-side `used`/`close` 처리 필요성은 공식 계약으로 확인한다. 의미를 추정해 상태 변경 요청을 추가하지 않는다.
- MUST: 새 실행은 기존 작업의 정리가 확인된 뒤에만 허용한다. API 계정 변경도 미정리 작업을 잃게 해서는 안 된다.

### 창 종료와 결과 불명

1. 유휴·성공·정리 완료 상태에서는 바로 닫을 수 있다.
2. 요청 중 또는 미사용 활성 번호가 있으면 작업 중단 및 정리를 시작하고 UI에 진행을 표시한다.
3. 정리 실패·시간 초과 시 “종료해도 서버 번호가 취소된 것은 아님”과 계정에서 확인하는 방법을 표시한다.
4. 사용자가 위험 안내를 확인한 뒤 강제 종료할 수 있다. 무기한 창 종료를 막지 않는다.
5. 앱 충돌·OS 강제 종료 후 자동 복구는 이번 범위에서 보장하지 않는다. 해당 한계와 계정 확인 방법을 문서화한다.
6. 구매 응답 유실은 재구매로 해결하지 않는다. 활성 ID를 모르는 경우에도 결과 불명으로 멈춘다. 제공자가 조회·멱등성 기능을 지원하는지 확인하고 지원이 없으면 수동 확인 경로를 제공한다.

## 5. 요구사항과 수용 기준

| ID | 수준 | 요구사항 | 통과 기준 |
|---|---|---|---|
| LIFE-01 | MUST | 상태·실행 식별자 도입 | 4절의 정상·실패·경합 시나리오가 일관되고 stale event가 무시됨 |
| LIFE-02 | MUST | 중지·종료 후 활성 번호 유지·정리 | 늦은 발급 응답을 잃지 않으며 취소 실패를 완료로 표시하지 않음 |
| LIFE-03 | MUST | 수동 거절 직렬화 | 거절 성공 뒤 추가 폴링·중복 거절 없음, GUI 멈춤 없음 |
| COST-01 | MUST | 재시도·발급·시간 상한 | 각 한도 도달 뒤 구매 요청이 더 발생하지 않음 |
| COST-02 | MUST | 가격 상한·구매 확인 | maxPrice·통화가 검증된 형식으로 전송되고 누락·잘못된 값은 구매 전 차단 |
| COST-03 | MUST | 불명확한 구매 결과 보존 | 타임아웃·비정상 응답 후 get-number 자동 재전송 없음 |
| API-01 | MUST | limits 계약 수정 | 공식 목록 fixture의 numbers를 읽고 선택 국가·서비스와 정확히 매칭 |
| API-02 | MUST | 입력·응답 검증 | 잘못된 ID·금액·횟수, JSON 타입 오류, 필수 필드 누락을 사용자 오류로 처리 |
| API-03 | MUST | 통신 예외·크기 제한 | timeout·접속 종료·잘못된 UTF-8·JSON·HTTP 오류 처리, 응답 본문 1MiB 초과 거부 |
| API-04 | MUST | 재시도 정책 분리 | 재고 없음만 정해진 간격 재시도. 인증·잔액 오류는 중단. 429는 안내 후 중단하여 재시도 폭주 없음 |
| SEC-01 | MUST | 오류 정보 최소화 | 원문 HTTP/JSON/URL을 기본 출력하지 않고 allowlist 오류 코드로 사용자 메시지 생성 |
| SEC-02 | MUST | 토큰·코드 비저장 | 파일·로그·traceback·테스트 아티팩트에 토큰·인증코드가 나타나지 않음 |
| SEC-03 | MUST | HTTPS·호스트 제한 | 운영 요청은 api.sms-man.com의 HTTPS만 허용. 리디렉션 차단, TLS 검증 유지 |
| SEC-04 | SHOULD | POST 본문 사용 | 공급자 지원 검증 후 전환. 미지원이면 GET 유지 이유·노출 감소책 기록, 조용한 fallback 금지 |
| PRIV-01 | MUST | 복사·마스킹·지우기 | 자동 복사 기본 OFF, 활동 기록 번호 마스킹, 유휴 시 민감정보 전체 지우기 제공 |
| PRIV-02 | MUST | 클립보드 한계 안내 | 앱이 쓴 현재 값만 선택적으로 삭제. 다른 앱이 덮어쓴 값 삭제 금지. OS 기록·동기화 완전 삭제를 약속하지 않음 |
| UX-01 | MUST | 상태별 동작·한국어 오류 | 현재 상태·다음 동작·복구 방법을 이해할 수 있고 네트워크 요청 중 창이 응답함 |
| UX-02 | MUST | Windows 사용성 | 키보드 탭 이동, Escape 중지, Enter는 유휴에서만 시작, 100/125/200% 배율에서 핵심 조작 가능 |
| DOC-01 | MUST | 안내·지원 문서 | 7절 문서가 구현과 일치하고 앱에서 열 수 있음 |
| REL-01 | MUST | 자동 테스트·비밀정보 검사 | Windows CI가 실제 회귀 테스트 실행, tracked files·전체 Git 이력 검사 결과 보관 |
| REL-02 | MUST | 배포 후보 재현성 | 버전·소스 SHA·빌드 방법·실행 방법·변경 이력·해시가 일치 |
| QA-01 | MUST | 4개 독립 리뷰 | 10절 전달 계약 충족 및 최종 커밋에 대한 검증 증거 존재 |

API-01 세부: 빈 목록은 재고 0으로, 해당 조합 없는 응답은 재고 없음으로 처리한다. 다른 국가·서비스의 재고를 대신 보여주지 않는다. 객체 `count` 형태는 공식 근거 또는 민감정보 제거된 실측 근거가 있을 때만 호환 지원한다. 목록 중 중복 조합의 합산 가능 여부가 불명확하면 임의 합산하지 않고 계약 확인 대상으로 보고한다.

API-02 세부: ID는 정수 문자열로 검증한다. 국가 0은 공식 문서상 무작위 국가이므로 이번 버전은 차단한다. 통화별 금액 단위·소수 허용·maxPrice 의미를 확인하고 Decimal로 검증하며 임의 반올림하지 않는다. 표시 가격과 상한 가격의 단위를 동일하게 한다.

SEC-02 한계: 메모리 참조 정리는 가능하지만 Python 문자열 메모리의 완전 소거와 OS 덤프·클립보드 기록 삭제는 보장하지 않는다. 테스트에는 합성 토큰·번호만 사용한다.

- MUST: 빌드·릴리스 후보는 로컬 또는 draft로 준비하며 실제 공개·태그·배포는 최종 출시 결정 뒤 수행한다.

- SHOULD: Windows 코드 서명은 배포 규모에 맞게 검토한다. 서명하지 않았다면 미서명 사실을 명시하고 보안 기능 해제를 설치 절차로 안내하지 않는다.
- LATER: 국가·서비스 이름 검색, 잔액 수동 조회, 접근성 개선, 자동 업데이트. 별도 요구사항 없이 이번 범위를 확대하지 않는다.

## 10. 무맥락 4개 병렬 코드 리뷰·QA 계약

### 실행 시점과 격리

2단계 구현 및 자체 검증 뒤에만 시작한다. 지금은 에이전트를 실행하지 않는다.

- 서브 에이전트 4개를 `fork_turns="none"`으로 생성한다. 대화·기존 리뷰 결론·작성자 해설을 전달하지 않는다.
- 모두 동일한 후보 SHA의 읽기 전용 소스 snapshot을 사용한다. 테스트 임시 파일은 에이전트별 경로에 둔다. 공동 코드 수정·실제 API 호출·외부 메시지 발송은 금지한다.
- 모든 리뷰에 본 스펙, 기준/후보 SHA, 소스 경로, 테스트 명령, 환경 제약을 전달한다. 전체 스펙은 독립적 검증 기준이므로 무맥락 전달 대상에 포함한다.
- 제출 전 에이전트끼리 결론을 공유하지 않는다. 작성자의 자체 PASS 판정은 전달하지 않는다.
- 필요한 근거는 각자 코드·테스트·공식 자료에서 확인한다. 실행할 수 없는 항목은 BLOCKED 또는 NOT_RUN이다.

|---|---|---|
| A. 보안·개인정보 | SEC, PRIV, 보안 설정 | 토큰 경로·오류·리디렉션·클립보드·문서의 과장 여부 |
| B. 상태·비용 | LIFE, COST | 중지·종료·거절 경합, 중복 구매, 결과 불명, 횟수·가격·시간 제한 |
| C. API·테스트 | API, 회귀 테스트 | 공식 응답과 fixture 일치, 파서·timeout·실패 모드, 테스트가 결함을 실제 검출하는지 |

- [ ] 기존 회귀 및 필수 모의 실패 시나리오 통과
- [ ] 실제 API 계약 미확인 항목과 Windows 실측 항목 해소, 미해소 시 배포 BLOCKED
- [ ] 4개 독립 리뷰 제출 및 수정 영향 재검증 완료
- [ ] 라이선스·비공개 문의처·배포 형태 확정
- [ ] 문서의 토큰·비용·정리 동작 설명이 코드와 일치
- [ ] 배포 후보의 버전·SHA·해시·검증 결과 일치

최종 보고는 다음 순서로 작성한다.

1. 판정: READY / NOT_READY / BLOCKED 및 핵심 이유
2. 기준 SHA, 최종 SHA, 배포 후보 버전과 산출물
3. 구현 변경과 요구사항별 PASS/FAIL/BLOCKED/NOT_RUN 추적표
4. 4개 리뷰 결과 요약과 결함별 해결·보류 표
5. 실행한 테스트·환경·명령·결과, 실제 API 및 Windows 검증 범위
6. 남은 위험·운영자 결정·사용자 수동 확인 사항
7. 공개 배포 여부: 실제 수행했는지 명확히 기재
